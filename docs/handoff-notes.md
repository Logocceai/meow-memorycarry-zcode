# 交接笔记:时机与注意事项

[中文](handoff-notes.md) | [English](handoff-notes.en.md)

> 面向使用者:什么时候该主动交接、交接时要注意什么。
> 两条指令的交互细节与档位说明见 [使用手册](user-guide.md)。

## 为什么交接要由人来决定

本插件刻意做成**指令触发**,而不是 hook 自动注入。这是设计,不是没做:

- **摘要必须先精炼再保存。** 窗口里哪些信息值得带走、哪些只是过程噪音,只有身处任务中的人判断得准。
- **载入是刻意行为。** 新窗口不一定需要上一次的全部记忆,由你选择载入哪份,比自动灌进去更省 token,也更不容易跑偏。

反过来说,**上下文快满时的自动压缩也在替你"总结"**——它不认识你的任务,只能按通用策略摘要,丢什么由它决定,而丢掉的往往正是细节:文件路径、之前定好的约定、报错原文。所以关键不是"要不要压缩",而是**由谁来压缩**。

由此引出一条硬约束:交接这个动作本身也要消耗上下文(要读记忆库、扫计划、写快照),所以它必须发生在**还有余量**的时候。等到快满了才交接,可能做到一半就撞上自动压缩,而压缩会先把你要总结的东西摘要掉。

## 什么时候该交接

四类时机,任一命中即可:

| 时机 | 说明 |
|---|---|
| 上下文到 70–80% | 最主要的信号:当前任务收尾后换窗口,不要继续硬撑 |
| 一个里程碑完成 | 功能写完、缺陷修完、方案敲定 |
| 踩完坑之后 | 刚解决的报错和它的根因,是快照里最值钱的内容 |
| 当天收工前 | 留一份"明天从哪继续" |

除了看百分比,**行为信号出现得更早**:重复读同一个文件、忘了之前定好的规则、回答开始变含糊——出现任一条就该着手交接,哪怕余量看起来还够。

## 什么时候不需要交接

- **任务还剩一两轮就结束**:交接要读记忆库、扫计划、写快照,这一轮读读写写的成本收不回来,做完直接收尾更划算。
- **零碎问答、日常闲谈**:没有决策、没有坑、没有断点,交接出来只是流水账。一次有信息量的交接胜过十次敷衍的。

## 注意事项

### 交接前

- **先 `/checkpoint`,再 `/handoff`。** 代码进度归 git,软知识归记忆库。顺序反了会出现"记忆里写着做完了、代码却没提交"的脱节。`/handoff` 检测到未提交改动时会提醒你先提交。
- **给交接留足上下文余量。** 理由见第一节:交接本身也吃上下文,快满时做最容易出事。

### 交接中

- **中途交接,`Next` 必须可执行。** 任务没做完就要换窗口时,快照的 Next 节要写到"下一步动哪个文件、做什么、什么还没验证"的粒度。含糊地写"继续完成任务",新窗口就得从头摸索,交接等于白做。
- **让它记真实发生的事。** 记忆库的底线是不编造:没验证的猜测不会被写成事实。发现记忆里有不实内容就直接指出,按实际情况修正。

### 交接后

- **看一眼报告再关窗口。** `/handoff` 结束时会报告本次档位、新建/更新了哪些文件、归档了哪些旧快照、当前活跃任务与下一步。扫一眼能发现两类问题:档位选错了,或某条该记的信息没进去。
- **确认写进了当前仓库。** 记忆库固定在**当前工作仓库**的 `.zcode/memory/`,换目录就是换记忆库。在错误目录交接,等于把记忆写到了别处。

## 交接之后怎么接

新窗口输入 `/recall`,它会先列出历史快照清单让你挑选(而不是直接塞最新那份),载入后给出一段进度摘要与下一步建议,你确认后继续干活。

典型轮回:`/checkpoint` → `/handoff` → 关窗口 → 新窗口 `/recall`。
