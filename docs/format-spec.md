# meow-memorycarry 记忆格式规范

记忆库是每个仓库一份的分层 Markdown 目录,固定位置 `<仓库根>/.zcode/memory/`。所有写入(由 `/handoff`)与读取(由 `/recall`)都必须遵守本规范。

## 1. 目录结构

```
.zcode/memory/
├── INDEX.md      # 唯一入口:活跃任务、下一步、最近快照列表
├── project.md    # 项目层:目标、进行中任务的状态
├── facts.md      # 事实层:原子事实(路径、命令、版本、环境约束)
├── decisions.md  # 决策层:已拍板的决策与理由,append-only
├── lessons.md    # 教训层:踩过的坑、错误与修复方式
├── handoffs/     # 交接快照,每次 /handoff 一份
└── archive/      # 已吸收的旧快照,git mv 移入,永不删除
```

## 2. 文件级格式

每个分层文件与快照都以 YAML frontmatter 开头:

```yaml
---
summary: 记忆库初始化与v1实现
created: 2026-09-15 08:27
updated: 2026-09-15 08:27
status: active
---
```

- `summary`:一句话概括文件内容(建议 ≤20 字)。快照的 `summary` 必须与正文标题、文件名三者同源;分层文件用一句话概括当前内容。
- `created`:创建时间 `YYYY-MM-DD HH:MM`。**快照列表排序一律按此字段**,与文件名无关。
- `updated`:最后写入时间,写一次更新一次。
- `status`:分层文件恒为 `active`;快照可为 `active` / `absorbed`(内容已合并进分层文件)/ `archived`(已移入 archive/)。

分层文件正文按小节组织,每个记忆条目遵守:

- **一条一事**:一个条目只讲一件事,一段话或一个 bullet,不写流水账。
- **带日期**:条目以 `[YYYY-MM-DD]` 前缀开头,便于按新旧取舍。
- **自包含**:条目必须脱离本会话语境仍能看懂——写具体文件路径、命令、commit hash,不写"刚才那个问题""上面说的方案"。
- **总结体**:先结论后细节,删除语气词、过程叙述与寒暄;超过 3 行的条目必须压缩。
- **语言**:条目用中文;代码、路径、命令、标识符保持原样。

## 3. 各分层文件的内容约定

| 文件 | 收什么 | 不收什么 |
|---|---|---|
| INDEX.md | 活跃任务列表(≤5 条)、下一步、最近 5 份快照索引 | 任何细节,细节放分层文件 |
| project.md | 项目目标、模块结构变化、进行中任务状态 | 一次性调试细节 |
| facts.md | 环境约束、关键路径、可复用命令、版本号 | 会随任务消失的临时状态 |
| decisions.md | 拍板过的决策 + 一句话理由(谁定的可不写) | 尚未决定的选项罗列 |
| lessons.md | 踩坑现象、根因、修复方式 | 未经验证的猜测 |

## 4. 交接快照(handoffs/)

文件名:`<概括>.memo.md`,如 `记忆库初始化与v1实现.memo.md`。概括即正文标题与 frontmatter `summary`,一句话建议 ≤20 字;清理文件系统非法字符(`/ \ : * ? " < > |` 与换行),空格转连字符;概括重复时在末尾加 `-2` 序号区分。时间**不进文件名**——排序一律按 frontmatter `created`,文件名只负责可读。概括使用记忆条目语言(中文),快照文件名是仓库 kebab-case 规范的插件内例外。`.memo.md` 双后缀用于一眼识别记忆文件与 `ls *.memo.md` 过滤。

快照固定六节模板(见技能目录 `templates/handoff-snapshot.md`),顺序不得改动:

1. `Summary` — 3 句以内概括本次会话做了什么
2. `Done` — 已完成事项,每条带提交 hash 或文件路径
3. `Decisions` — 本次拍板的决策与理由
4. `Pitfalls` — 踩过的坑与规避方式
5. `Next` — 下一步,写成新会话可直接执行的指令
6. `Refs` — 相关文件路径、commit、外部链接

## 5. 行数硬上限

| 对象 | 上限 | 超限处理 |
|---|---|---|
| INDEX.md | 80 行 | 合并活跃任务、裁剪快照索引 |
| 单份快照 | 150 行 | 压缩条目,细节移入分层文件 |
| 单个分层文件 | 120 行 | 合并同类条目、删除已被取代的旧条目 |

写入前先数行数;超限必须先精简再写入,不允许"以后再整理"。

## 6. 生命周期与清理

快照状态机:`active → absorbed → archived`

1. 新快照写入时为 `active`。
2. `/handoff` 写入新快照的同时,把旧 `active` 快照中仍然长期有效的信息(事实、决策、教训)合并进对应分层文件,然后把这些快照 frontmatter 的 `status` 改为 `absorbed`。
3. `absorbed` 且 `created` 距今超过 14 天的快照,在下次 `/handoff` 时用 `git mv` 移入 `archive/` 并把 `status` 改为 `archived`。**只移动,不删除**——历史由 git 保留。
4. `/handoff tidy`(整理模式)可随时手动触发:去重分层文件、合并同类条目、强制执行行数上限、批量归档过期快照、重建 INDEX.md。

分层文件永不移入 archive;过期内容直接改写或删除条目本身(条目级内容更新属于编辑,不属于删除文件)。

## 7. 与其他机制的关系

- **代码进度归 `/checkpoint`**:记忆库只存知识与状态,不存代码本体。`/handoff` 发现未提交改动时,提示先执行 `/checkpoint`。
- **会话计划 `.zcode/plans/plan-sess_*.md`**:与本记忆库互不覆盖;`/handoff` 可在快照 `Refs` 中引用相关 plan 文件路径。
- **记忆库必须进 git**:这是跨机器同步与历史回滚的唯一手段。安装该技能的仓库若尚未跟踪 `.zcode/memory/`,首次 `/handoff` 时一并 `git add`。
