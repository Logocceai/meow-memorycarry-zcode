# handoff 与 compact 对比:什么时候该用哪一个

[中文](handoff-vs-compact.md) | [English](handoff-vs-compact.en.md)

> 本文是选型依据,不是宣传材料。结论基于 2026-09-15 ~ 2026-09-18 的真实会话实测:107 次 `/compact` 调用、7 次 `/handoff` 调用、10 次 `/recall` 调用,同一工作区、同批模型(`deepseek-v4.1-flash` / `deepseek-flash`)。
> 相关:[Token 节省与档位成本实测](token-report.md)、[交接笔记:时机与注意事项](handoff-notes.md)

---

## 1. 先说结论

**如果你只是想让当前这个窗口继续跑下去,不需要跨窗口记忆、不需要版本控制、不需要本地记忆库、不需要多机共享——直接用 ZCode 内置的 `/compact`,它明显比 `/handoff` 更合适。**

理由是成本差两个量级:`/compact` 是一次模型调用,`/handoff` 是一轮多步操作(读记忆库、写快照、提交、出报告)。实测非缓存输入 1,347 tokens vs 252,819 tokens,模型耗时 25 秒 vs 190 秒。

**反过来,以下四件事只有 `/handoff` 能做,`/compact` 一件也做不到:**

1. **跨窗口**。`/handoff` 的产物是文件,新窗口 `/recall` 可以载入;compact 的摘要只活在那一个会话里,换个窗口就看不见。
2. **版本控制**。记忆库存进仓库、随 git 走,可 diff、可回退、可审计;compact 的产物在客户端数据库里,不在任何 git 仓库内。
3. **本地长期记忆**。分层文件(`project` / `facts` / `decisions` / `lessons`)跨窗口吸收合并,知识随使用变厚;compact 每次只覆盖当前窗口,不累积。
4. **多机共享**。记忆库跟着仓库同步到别的机器;compact 的产物不可移植。

所以这不是"谁更好"的问题,而是**你需不需要那四件事**的问题。

## 2. 机制差异

| 项 | `/compact`(内置) | `/handoff`(本插件) |
|---|---|---|
| 触发 | 手动输入,或上下文到阈值时自动 | 手动输入(口语触发同样生效) |
| 产物位置 | 客户端会话库,摘要作为一条消息挂进时间线 | 仓库文件 `.zcode/memory/handoffs/<概括>.memo.md` |
| 产物结构 | 固定 9 节(请求与意图、技术概念、文件与代码段、报错与修复、问题解决、全部用户消息、待办、当前工作、下一步) | 固定 6 节(Summary / Done / Decisions / Pitfalls / Next / Refs) |
| 丢弃策略 | 被覆盖的消息不再进上下文;最近消息原样保留 | 快照有 150 行上限,主动丢细节,靠 `Refs` 指针与 git 兜底 |
| 参数 | `/compact [instructions]`,可临时指定保留重点 | `/handoff sN dM`,速度轴 × 深度轴共 9 档 |
| 跨窗口 | 无 | 有,`/recall` 载入 |
| 版本控制 | 无 | 有,随仓库 git |
| 与回退系统 | 压缩点之前的回退目标会降级(只能还原文件,或不可用) | 不触碰回退系统 |

补充一点容易误解的:压缩**没有删掉原文**,原文按内部行号留在本地库里;但那些标识只服务客户端自身的回退与界面,摘要正文里没有任何"原文在哪"的引用。

## 3. 成本实测

### 3.1 口径

- **一次 `/compact`** = 一次模型调用;一次 `/handoff` / `/recall` = 该指令轮内触发的全部模型调用(中位 16 次 / 10 次)。
- `computed total = input + output`(逐行核验);**缓存命中是 input 的子集**,计费远低于新输入,因此单列"非缓存输入"。
- 各列独立取中位数,所以"中位 input + 中位 output"不等于"中位 computed total";单行数据严格相加。
- 折算按字符估:中文 ×0.7、其他 ×0.25。

### 3.2 单次操作成本

| 指标 | `/compact`(n=107) | `/handoff`(n=7) | `/recall`(n=10) |
|---|---|---|---|
| 模型调用次数(中位) | 1 | 16(3–32) | 10(5–28) |
| input tokens(中位) | 19,139 | 4,266,771 | 535,139 |
| 其中缓存命中(中位) | 17,792 | 4,013,952 | 482,464 |
| **非缓存输入(中位)** | **1,347** | **252,819** | **52,675** |
| output tokens(中位) | 6,056 | 17,179 | 9,784 |
| computed total(中位) | 25,949 | 4,298,575 | 544,051 |
| 模型耗时(中位) | 24.9s | 190s | 122s |
| 耗时区间 | 11.7–77.3s | 47–401s | 35–365s |

作为参照,同库内**普通单轮对话**的中位数是 computed ≈11.4 万 tokens、耗时 ≈7.2s、output 616 tokens。`/compact` 的输出量约为普通轮次的 9.8 倍、耗时约 3.5 倍;`/handoff` 是一次多轮操作,总量约为普通单轮的 38 倍。

### 3.3 静态体量(折算)

| 项 | 数值 |
|---|---|
| compact 的摘要提示词模板 | 3,018 字符 ≈ 755 tok |
| compact 生成的摘要正文 | 中位 6,411 字符 ≈ 2,718 tok(最大 19,546 字符) |
| 本插件记忆库分层文件合计 | 3,902 字符 ≈ 1,587 tok |
| 记忆库 9 份快照合计 | 21,851 字符 ≈ 8,769 tok |
| 典型 `/recall` 必读量 | INDEX 336 tok + 单份快照 476–1,624 tok |

摘要正文(≈2,718 tok)明显小于压缩调用的 output(中位 6,056 tok):差额是提示词要求的"先分析再总结"分析段与格式开销。

### 3.4 压缩比:compact 到底省了多少上下文

以"压缩调用的 input(压缩前上下文规模)"对比"压缩后首个主轮的 input":

| 压缩前上下文规模 | 样本 | 压缩后 / 压缩前(中位) | 区间 |
|---|---|---|---|
| < 20k | 59 | 105% | 92–131% |
| 20k–100k | 46 | 97% | 85–130% |
| > 100k | 2 | **29%** | 18–40% |

**小上下文下压缩并不省空间,反而略增。** 算术上能解释:某会话压缩前 15,686 tokens、压缩后首轮 17,478,净增 1,792;摘要正文约 2,718 tokens,推出被覆盖的历史只有约 0.9k——没多少东西可压。只有上下文真正接近上限(>100k)时,压缩才把规模降到三成以下。(机制解释为推断,未逐行核对上下文装配代码。)

### 3.5 连续压缩与失效

- 相邻两次压缩的间隔:中位 **31 秒**,71 次间隔中 69 次短于 180 秒。
- 110 次压缩调用中 3 次状态为 error。
- 压力期日志中出现 24 次"压缩后上下文在 3 个工具轮内回填"的熔断记录;这些事件只在实验期出现,其余日期为 0。

## 4. 使用场景判定

| 情形 | 选择 | 理由 |
|---|---|---|
| 上下文接近上限,任务还要在本窗口继续 | `/compact` | 只需要续命,不需要跨窗口资产 |
| 一个可交付单元完成 / 当天收工 / 要换窗口 | `/handoff` | 收益在下一个窗口兑现 |
| 要换机器继续 | `/handoff` | compact 产物不可移植 |
| 任务还剩一两轮就结束 | 都不用 | 交接收不回成本;压缩也白花 |
| 会话很长、任务未完成,必须换窗口 | 先 `/handoff` | 先把信息带出去,再谈腾空间 |
| 水位已紧张到做不完交接 | 先 `/compact`,再 `/handoff` | 代价:这次压缩会降低此后回退能力,且被覆盖的细节不再进上下文 |
| 零碎问答、无决策无断点 | 都不用 | 交接只会产出流水账 |

组合用法要认清代价:`/compact` → `/handoff` 能解决"水位不够做交接",但压缩点之前的回退能力已经降级,**交接时能读到的原文已经少了一部分**。

## 5. 各自优势

### `/compact` 的优势

1. **零准备、零依赖**。任何会话都能用,不需要建立记忆库、不需要写规范、不需要养成习惯。
2. **自动兜底**。到阈值自动触发,人顾不上上下文时它是唯一在工作的机制。
3. **单位成本低**。一次调用、中位 25 秒、非缓存输入中位约 1.3k tokens。
4. **单次信息颗粒度高**。提示词要求完整代码片段、函数签名、全部用户消息、报错与修复,还要求把安全约束逐字保留——比 150 行上限的快照更细。
5. **近期消息原文保留**,减少"刚说过的事被摘要扭曲"的风险。
6. **可临时指定重点**(传 instructions)。

### `/handoff` 的优势

1. **跨窗口、跨机器可用**。产物是可读文件,随 git 走。
2. **面向任务选择,而非面向转录**。Done / Decisions / Pitfalls / Next 按"下一个任务需要什么"组织。
3. **可累积**。分层文件跨窗口吸收合并,知识变厚。
4. **可回退、可审计**。`git log`、`git revert`、归档走 `git mv`。
5. **主动时机 + 写后自检**。可在水位宽裕时执行,避开压力下生成。
6. **有失效兜底指针**。快照丢细节,但 `Refs` 指回文件与提交,细节可追回。

---

## 6. 各自劣势

### `/compact` 的劣势

1. **与任务无关**。它不知道你在做什么,丢什么由通用模板决定。
2. **本会话之外没有价值**,不构成可检索的记忆。
3. **削弱回退能力**。压缩点之前的回退目标会降级,文件可还原、会话内容不一定。
4. **压力下自身会退化**。历史过大时提示词过长,实现会丢弃更早轮次后重试。
5. **可能白花**。小上下文下压缩后规模约为压缩前的 105%,花了约 2.6 万 tokens 却没省空间;连环压缩(中位间隔 31 秒)属于净损耗。
6. **熔断后不再救场**,此后上下文压力由人承担。
7. **不可移植、不可版本化**。

### `/handoff` 的劣势

1. **必须人工判断时机**。判断错了就白花。
2. **单位成本高出两个量级**。非缓存输入中位约 25.3 万 tokens、模型耗时中位 190 秒(其 input 中 94% 是缓存命中)。
3. **需要在有余量时执行**。它自己就吃上下文,等到快满了才做可能做到一半撞上自动压缩。
4. **没有自动化触发**。新窗口不 `/recall` 就等于没交接。
5. **依赖模型遵守技能定义**。档位、行数上限、命名规范都靠模型执行。
6. **丢弃是强制的**。150 行上限意味着完整代码片段、逐字用户消息这类内容留不下来,这一点上不如 compact 摘要。
7. **需要长期维护**。分层文件要靠 `tidy` 去重、归档、重建索引。

## 7. 方法、来源与局限

### 数据来源

| 数据 | 来源 |
|---|---|
| compact 单次调用 token / 耗时、压缩比、连续压缩间隔 | 本机 ZCode 会话库的模型用量表(按 `query_source='compact'` 筛选)与消息表 |
| compact 摘要正文体量 | 会话库中标记为 Compact summary 的消息 |
| `/handoff`、`/recall` 指令轮成本 | 会话库中经"用户输入 → 消息 → 模型调用"链路精确归因 |
| 跨窗口收益、三档成本 | [token-report.md](token-report.md) 的 10 个隔离实验 |
| 压缩提示词模板、回退降级策略 | 客户端运行时包 `resources/glm/zcode.cjs` |
| 失效计数 | 客户端日志目录下的当日日志 |

### 局限

1. **样本期偏斜**。107 次 compact 调用全部发生在 2026-09-15(记忆实验期);`/handoff` 实测的 7 次集中在 09-16、09-17。两者同模型、同工作区,可比性较好,但都不代表长期日常使用。
2. **`/handoff` 的 n 很小(7)且方差大**。同一操作在 3–32 次调用、47–401 秒之间波动,取决于会话长度与记忆库规模。中位数可看,不宜当常数。
3. **归因口径包含工具循环**,不等于"纯指令开销"。
4. **两侧测量精度不同**。compact 是单次调用,隔离干净;handoff 是多步操作,只能整轮归因。
5. **折算系数是经验值**(中文 ×0.7、其他 ×0.25),换精确分词器会改变绝对值,不改变对比关系。
6. **未核实项**:最近消息保留的具体条数;压缩比在 >100k 档位仅 2 个样本;回退降级各档的完整触发条件。
